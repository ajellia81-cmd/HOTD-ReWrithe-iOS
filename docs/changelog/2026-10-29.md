# Changelog 2026-10-29

## rescrash: the resolution crash, crash reports for every crash, Display Mode (Borderless)

A player's friend (RTX 4070 laptop, 480 Hz display): "pressed a resolution and it crashed". His log
(hotd.prev.log) ends in the menu with no crash line, and no crash-*.txt was written.

What the log shows:

- The game ran on the laptop's **integrated Radeon 610M**, not the RTX 4070 ("live background: AMD Radeon(TM) 610M
  (integrated / software graphics)"). A laptop with two GPUs gives OpenGL the fast one only to a program that asks
  for it, and the game did not ask. Changing the display mode with OpenGL on the integrated GPU while the 480 Hz
  panel is driven through the other one is where graphics drivers fail.
- The live attract reloads in the log (23:55:50-58) were mod On / Off changes and Blood Color changes, not the
  resolution; the resolution press came after the last log line (a window size or a display mode change logs
  nothing before it is done).
- No report: the crash handler is installed for every run (not only some), but a crash Windows ends at once (heap
  corruption, a driver's fail-fast) never reaches any handler, and a graphics driver / overlay can replace the
  handler after the game starts.

| | Before | After |
|---|---|---|
| Laptop with NVIDIA / AMD graphics + integrated GPU | OpenGL on the integrated GPU (slow; the Live Background Auto off; mode changes through the weak driver) | the game asks for the fast GPU (NvOptimusEnablement / AmdPowerXpressRequestHighPerformance exports) |
| A crash no handler sees (fail-fast, heap corruption, the game killed) | no report at all | the next start writes `crash-<date>-<time>-previous-run.txt` with the last 80 lines of that run's log (a `hotd.running` marker while the game runs; removed at a normal end) |
| Another module replaces the crash handler | crashes after that: no report | the game's handler is set again after the graphics start, after each display change and every second (logged once per module) |
| Crash report written | the stack walk first, then the file | the error and the last log lines first (flushed), the stack after: a failing stack walk still leaves a report |
| Video > Start Fullscreen (On / Off) | borderless; a chosen fullscreen resolution meant exclusive | **Video > Display Mode: Windowed / Borderless / Fullscreen**, applied at once, kept for the next start |
| Video > Resolution | fullscreen: Auto = borderless, a size = exclusive | Windowed: the window's size; Fullscreen: the display mode (Auto = the desktop's, exclusive); Borderless: the desktop's (the row is greyed, saying so) |

- launcher.ini: `displaymode=` 0 Windowed / 1 Borderless / 2 Fullscreen (the start's mode; F11 still keeps the way
  you left it), `exclusive=` (the fullscreen F11 goes to from a window). `fullscreen=` is still written. An older
  launcher.ini with a chosen fullscreen resolution starts in Fullscreen (exclusive), as before.
- Texts in en / ko / ja / ar / he (machine-translated like the rest).
- A hidden window (the tests) never changes the display's mode: Fullscreen is only noted there.
- New input-test steps (Remake walk, acts 41 / 42, twice): Models flipped twice (the live attract loads again each
  time; Chapter 1's view prepared ahead on a worker as the menu does) while every frame sets another window size,
  Windowed / Borderless / Fullscreen or presses F11, at an uncapped menu rate; then a window of the size it had,
  and the live attract running again.
- Crash handler tests: `HOTD_CRASH_TEST=2` (a crash after the window and the graphics are up: report written),
  `HOTD_CRASH_TEST=3` (a fail-fast no handler sees: the next start writes the previous-run report).
- Not reproduced here: the crash itself (a single-GPU PC; the driver's own failure). If it happens again, the next
  start now leaves a report.

- The friend's pop-ins and fades: no frame-rate cause found. A hidden window at 480 fps with the shots one loop after
  the tick (`HOTD_SHOT_LATE`) and the same frames at 60 fps (Chapter 1 f1300-6400, arcade, Smooth Motion on) give the
  same textures, fades and pieces (only the random rain differs); the view's per-draw code only reads the game's state
  (texture area, colour rows, fades and zones change with the ticks). His logs show the game ran on the laptop's
  integrated **Radeon 610M** (see rescrash), so the **depth pre-pass was on** (on for integrated graphics only: why

  Fix: `invariant gl_Position` in the vertex shader. Checked here (NVIDIA): pre-pass on / off pictures identical
  (Chapter 1 f2500 / 5000 / 6400, 4-19). Not checked on an AMD integrated GPU (none here); `HOTD_PREPASS=1` forces the
  pre-pass on for a test.

## angle: a DirectX renderer (ANGLE) for PCs without OpenGL 3.3

Pre-2012 graphics (Intel HD 2000 / 3000, older AMD / NVIDIA) often have DirectX 10.1 / 11 but no OpenGL 3.3 driver,
so the game could not start there. The Windows build now also draws through ANGLE (Google's OpenGL ES 3.0 to
Direct3D 11 translator). Details: docs/renderer_backends.md.

| | Before | After |
|---|---|---|
| Graphics without OpenGL 3.3 | "the driver does not offer OpenGL 3.3", no game | Auto starts through DirectX 11 (ANGLE), feature level 10_1 or newer |
| Options > Video | no choice | **Renderer**: Auto / OpenGL / DirectX (ANGLE) (next start; launcher.ini `renderer=`, `--renderer`) |
| DirectX 10.0 / 9 graphics | the OpenGL message | the message says OpenGL 3.3 or DirectX 10.1 is needed (ANGLE has only OpenGL ES 2.0 there) |
| OpenGL path | | unchanged: 40 Chapter 1 renders byte-identical before / after (the one shader edit gives the same result) |
| Package | | + libEGL.dll, libGLESv2.dll, z.dll: +5.7 MB, +2.1 MB zipped (NOTICE: ANGLE BSD-3, xxHash, zlib) |
| DirectX start / chapter load | | shaders compiled once (~1.3-1.9 s on an RTX 5080), then kept in `angle_shaders.bin` (13 ms) |

- Tested on the RTX 5080 only (NVIDIA through Direct3D 11): input test 2130 checks, 0 failed with `--renderer angle`;
  Chapter 1 renders (40 frames, arcade and PC models) and the CRT presets equal to OpenGL to rounding (PSNR 43-70 dB,
  differences only on triangle edges); the menu tour; Auto's fallback (`HOTD_GL_FAIL=1`) reaches the menu.
  Simulated: feature level 10_1 works (renders byte-identical to 11), 10_0 and Direct3D 9 refuse (ES 2.0 only),
  WARP (software) works at ~32 ms a frame.
- Not covered: GPU timer queries (the menu tour's GPU column reads 0 on DirectX), Windows 7 (this ANGLE needs Windows 8+).
- Checks (default OpenGL path, after merging main): `--input-test` 2130 checks, 0 failed; Chapter 1 "chapter 1 ended"
  at 16350 (arcade and PC models); 4P Chapter 1 22283; `--chapter 2 --strict --default-route`: 16550 / 48114;
  Chapter 4 strict "the ending is over" at 34967 (both models); 40 OpenGL renders byte-identical to the build before.
